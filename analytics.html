CHAPTER 04 · THE ARCHITECTURE LEDGER

Count the weights.
Then count the work.

A large parameter count does not tell you which part is slow. Separate model capacity, per-token work, memory traffic and communication to understand why transformer designs look the way they do.

01 / WHY THESE DESIGNS EXIST

Each change buys something different.

MLP: capacity between attention steps

Attention exchanges information between tokens. The MLP transforms each token’s features with shared weights. Standard attention has four d × d projection matrices; an ordinary f = 4d MLP has two larger matrices, totaling 8d². That gives the familiar 1:2 attention-to-MLP split—not a universal constant. [1]

Attention: 4d² · ordinary MLP: 2df

SwiGLU: learned feature interactions

Two projections see the same input. SiLU on one branch modulates the other branch feature by feature; W₂ contracts the product. The extra matrix costs parameters, but experiments found benefits even when the intermediate width was reduced to match the ordinary MLP budget. It is a useful inductive bias, not a guaranteed win in every setup. [2]

[SiLU(xW₁) ⊙ xW₃]W₂

At equal f: 50% more MLP weights. To match 2df, use f′ ≈ 2f/3; hardware-friendly rounding slightly changes the budget.

GQA: share keys and values

Queries keep their heads while groups share K/V heads. This shrinks K/V projections and the decoder KV cache. It does not shrink the query/output projections, the MLP, or the number of query-to-key comparisons. MQA is the single-KV-head endpoint. Quality and serving efficiency both matter. [3]

Attention: 2d² + 2d × (Hkv × dh)

MoE: more stored capacity, selective work

The router selects k of E MLPs per token. Each selected expert gets the complete input vector; outputs are weighted and added, not concatenated. More tokens in a batch can collectively activate every expert. Replicating experts does not make each individual expert smaller unless you choose to reduce f. [4]

Stored: E × Pexpert + dE
Active/token: k × Pexpert + dE

An MoE router gate chooses experts. A SwiGLU gate modulates features inside each expert. Both can coexist.

02 / SAME WEIGHTS, DIFFERENT WORKLOAD

Token count changes work, not weights.

The calculations below use the same-width SwiGLU MoE design from the Parameters comparison. Dense layers are the same formulas with E = k = 1 and no router.

Show FLOP and memory arithmetic

Prefill: many token rows at once

Projection work grows linearly with n. Full square attention mixing grows quadratically: QKᵀ and AV each cost about 2Bn²d FLOPs, so together they cost 4Bn²d per block. No learned parameters are added when n grows. A causal kernel that skips the upper triangle needs roughly half that mixing work for long sequences. [1]

Decode: one new query per sequence

With a KV cache, prior tokens’ K/V projections are reused. A new query still reads the context’s keys and values; mixing scales with context length. A small decode batch has little weight reuse, so memory traffic can dominate. Batching increases reuse but changes latency, memory pressure and scheduling. [3] [5]

What the memory estimates leave out

Weight storage is not a GPU fit guarantee. Add KV cache for decoder inference, transient activations, workspaces, allocator overhead and communication buffers. Training adds saved or recomputed activations, gradients and optimizer state; the multiplier depends on precision, optimizer, sharding and checkpointing. Encoder-only ViT/Pixtral vision blocks do not maintain an autoregressive decoder KV cache. The cache example here is specifically for a decoder.

For 8-bit storage, the numbers assume exactly one byte per scalar and omit scales, zero points and mixed-precision exceptions. This is not a promise that weights and KV cache can both use that format with no quality or kernel trade-offs.

03 / WHAT THE GPU ACTUALLY SEES

Moving numbers can cost more than multiplying them.

A GPU does not see “an expert” or “a reasoning feature.” It sees matrix operations, memory accesses, kernels and, sometimes, transfers to other GPUs. [5]

Tiled kernels reuse loaded data on-chip rather than fetching every scalar for every multiplication. Tensor Cores accelerate supported matrix operations; shapes, precision, alignment, occupancy and kernel implementation all affect utilization. Fusing activation/gating work can avoid intermediate memory traffic, but does not remove the learned projections. [5]

A roofline thought experiment—not a benchmark

For just the ordinary expansion GEMM: X[M,d] × W[d,f] → Y[M,f], with M = Bn. Assume each input/weight is read once and the output written once. That is a best-case traffic estimate, not a measured GPU implementation.

Show the roofline arithmetic

Hypothetical hardware inputs, not a named GPU. Use dense peak compute for the chosen precision, not a vendor’s structured-sparsity peak. The ideal lower bound is max(compute time, memory time), not their sum. Real latency also includes imperfect reuse/utilization, kernel launches, dependencies and transfers. Do not treat it as a prediction for the whole model. [5]

Why batch size changes the answer

One token turns a weight-heavy matrix operation into something close to matrix-vector work. Many token rows reuse the same weights. Try n = 1, B = 1, then B = 128: arithmetic intensity rises even though the parameter count stays fixed. A higher intensity can move this idealized operation from bandwidth-limited toward compute-limited. [5]

MoE: sparse at the expert level

Skipping whole experts is conditional computation; the selected MLPs still use dense matrices. It is not automatically the hardware’s supported 2:4 weight-sparsity pattern. Tokens must be grouped by expert before those dense or block-sparse kernels can run efficiently. [7]

Across GPUs: dispatch and return

If experts live on different devices, token vectors must be dispatched to the selected experts and their outputs returned for combination. Top-k can increase assignments and communication. Imbalanced routing creates stragglers; tiny per-expert batches waste throughput. Load balancing, grouped/block-sparse kernels and placement help, but do not abolish network costs. [4] [7]

FlashAttention: less traffic, same attention

A naïve implementation materializes an n × n score/probability matrix per head. FlashAttention tiles exact attention to reduce HBM traffic instead of storing that full matrix. It does not add/remove model parameters and does not turn exact dense attention into a linear-complexity approximation; the quadratic mixing arithmetic remains. The score-size estimate above is explicitly the naïve implementation, not a requirement. [6]

Choose the budget you mean.

  • Capacity: stored parameters. MoE grows this selectively.
  • Work: active projections plus attention mixing and other operations.
  • Memory: weights, cache, activations, workspaces—not just one count.
  • Latency: hardware utilization, memory/network traffic and scheduling. Measure it.
